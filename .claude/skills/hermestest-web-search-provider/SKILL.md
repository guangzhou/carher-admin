# hermestest 实例侧 web_search provider 切换

适用形状：**188（`10.68.13.188` / jms 资产 `JSZX-AI-03`）上的 docker 容器实例**，
如 `hermestest-14`，openclaw `2026.6.10`。
⚠️ **不是 K8s 那套 carher 实例**（`carher-<N>-user-config` ConfigMap），那套见
`carher-instance-config-override`，两套的 `${ENV}` 语义相反，见下面 §2 的判别器。

## 0. 先跑量具，再动手

```bash
# 改动前存基线（既存故障必须先落袋，否则改完全都长得像「我搞坏了」）
scripts/hermestest-web-search-verify.py --save-baseline /tmp/h14.base.json
# 改动后
scripts/hermestest-web-search-verify.py --baseline /tmp/h14.base.json
# 自检：探测器自己报不出红，它就不是量具
scripts/hermestest-web-search-verify.py --no-home-fix   # 必须 EXIT=3
```

退出码：`0` 全过（L4 不参与）/ `1` 有层判红 / `3` 尺子坏了 / `4` 调用失败。

| 层 | 查什么 | 判红意味着 |
|---|---|---|
| L0 | `config get gateway` 读得到 | **尺子坏了，不是功能坏了** —— 立刻停，别读下面任何层 |
| L1 | `config validate` + 读回键集 + 热重载日志 | 改动没被装载 |
| L2 | `infer web search --query` 实打 | **唯一能证明 `${VAR}` 插值成功的层** |
| L3 | 容器健康 + 既存故障签名 delta | 只有 `NEWLY BROKEN` 才是我搞的 |
| L4 | 真实 turn 的 dispatch 区间 | **永远 MANUAL，脚本不给绿** |

## 1. 改哪个文件

```
/Data/carher-runtime/deploy/carher-<N>/openclaw.runtime.json5
   → 容器内挂到 /data/.openclaw/openclaw.json
```

配置分三层：`base.json5` + `docker.json5`（都是 CI/CD pin 的共享挂载，**不许改**）
+ 每实例 `openclaw.runtime.json5`（血半径 = 单实例）。
跨层**对象递归合并**，加子键不会冲掉 base 的兄弟键；
⚠️ **数组是替换语义**，`plugins.load.paths` 这类绝对别在 overlay 里重声明。

**正确路径是 `plugins.entries.<plugin>.config.webSearch`。**
`tools.web.search.<provider>` 已 legacy，loader 直接拒：

```
× tools.web.search.perplexity: legacy web_search provider config must use
  plugins.entries.<plugin>.config.webSearch
```

🔴 **dist 里的运行时读取路径 ≠ 配置面该写的路径**（中间有兼容层
`configContracts.compatibilityRuntimePaths`）。**判该写哪只认 `openclaw config validate`，
grep dist 会把你带到 legacy 路径上去。**

字段形状由插件自己的 `openclaw.plugin.json#configSchema` 给定。
perplexity 是 `additionalProperties:false` 的 `{apiKey, baseUrl, model}` **恰好三个键**
—— 多一个键整块无效（量具 L1 就断言这个键集）。

实例 14 的成品（锚点注释 `@pplx-via-litellm`）：

```json5
perplexity: {
  enabled: true,
  config: {
    webSearch: {
      apiKey: "${CARHER_PROD_KEY}",
      baseUrl: "https://cc.auto-link.com.cn/pro/v1",
      model: "perplexity-sonar",     // 网关侧组名，不是上游真名
    },
  },
},
```

改之前先 `cp` 一份 `openclaw.runtime.json5.bak-<tag>-<ts>`，回滚 = `cp` 回来。

🔴 **该文件头写着 `// AUTOGENERATED DO NOT EDIT.`**，源是
`/Data/carher-runtime-orchestra/deploy/bots/carher-<N>.s3.json`，
而 manifest 里**没有自由注入位** ⇒ **一次 redeploy 就冲掉，且零症状**
（静默回落到 `OPENROUTER_API_KEY`，搜索照样"能用"）。要长期生效必须改生成器。

## 2. `${VAR}` 插值：两套形状语义相反

| 形状 | overlay 里的 `${ENV}` | 判别器 |
|---|---|---|
| **188 docker**（本 skill，openclaw 2026.6.10） | **会插值**，任意路径 | `docker exec -e HOME=/data <c> openclaw infer web search --query …` 返 200 且正文非空 |
| **K8s user-config**（`carher-instance-config-override`） | **不插值，原样保留 → 401** | 同上但返 401 |

188 这套的依据：`dist/env-substitution-*.js` 的 `resolveConfigEnvVars(obj, env)`
走 `substituteAny`，对整个已解析 config 对象递归（字符串/数组/普通对象全走），
注释写明 "after JSON5 parse and `$include` resolution"。
未设或空值抛 `MissingEnvVarError`（**不是静默空串**）。

⚠️ 两条都是实测结论，**别把任一条外推到另一套形状**；不确定时就跑判别器。

容器内可用的 env（实例 14）：`CARHER_PROD_KEY`(len 25, 前缀 `sk-PbuAK`)、
`OPENROUTER_API_KEY`(len 73)、`PERPLEXITY_API_KEY`(**len 0**)。
插件 manifest 的 `setup.providers[0].envVars = ["PERPLEXITY_API_KEY","OPENROUTER_API_KEY"]`
⇒ 你的 `config.webSearch` 一旦被冲掉，它会**静默走第二个**。

## 3. 生效判据：热重载那行 log

改完约 30s，gateway 自己打：

```
[reload] config change detected; evaluating reload (plugins.entries.perplexity.config)
[reload] config hot reload applied (plugins.entries.perplexity.config)
```

**这行带具体路径，是「gateway 进程本身吃进了这个改动」的直接证据，比重启更好。**
`docker restart` 是多余动作。配置无效时 fail-closed：
`[reload] config reload skipped (invalid config): <reason>`。

🔴 **判 skipped 不能只看「日志里有没有」** —— 整条日志史里任何一次历史失败
都会让它永久判红。只有**最近一次 reload 事件是 skipped** 才是红
（量具里比的是两者的时间戳，同 tz ISO 串字典序即时间序）。

## 4. 坏尺子清单（这条路上我全踩过）

| 坏尺子 | 症状 | 真相 |
|---|---|---|
| `docker exec` 不带 `-e HOME=/data` | 每个键都 `Config path not found` | HOME=/root，CLI 没读到任何配置。**结构性假红**，阳性对照 = `config get gateway` |
| `openclaw infer web search "<问题>"` | `Missing required option "--query"` **且 exit 0** | 裸位置参数不吃，**假绿**。必须 `--query "<文本>"` |
| `openclaw config get …apiKey` 验插值 | 返 `__OPENCLAW_REDACTED__` | **config get 验不了插值**，只有 L2 实打能验 |
| 容器内 `curl 127.0.0.1:29131` | 返 `000`，像 gateway 死了 | 容器内是 **18789**，29131 是宿主映射 |
| `openclaw status` | 120s 挂死 | 别放判活路径。判活用 `curl 127.0.0.1:18789/health` → `{"ok":true,"status":"live"}` |
| gateway 日志 grep `web_search` | 今天零命中 | 那字样只出现在 `[antitalker]` 的 `tools=[...]` 行里，**不是调用本身的日志**。判走没走只能看 SpendLogs |
| grep `received from` | 「没收到飞书消息」 | 真串是 `received message from`。**grep 的字符串必须从真日志抄一行，别凭印象拼** |
| `config validate` 数告警用 `-` 起头 | 数出 0 条 | validate 用 `!` 起头，且自己声明 `N warning(s):`。**会数东西的量具必须先断言 `declared == len(提取到)`** |

## 5. L4：怎么证明真实 turn 走了这条路

**判据不是「上游出现了新调用」，是「每条调用都落在
`dispatching to agent` → `dispatch complete` 的区间内」。**

1. 容器日志取区间：
   ```bash
   docker logs --since 40m <c> 2>&1 | grep -E 'received message from|dispatching to agent|dispatch complete'
   ```
2. 198 上按 `key_alias` + `model_group` 查 SpendLogs（`-n litellm-product`），
   认 `completion_tokens > 0`（空壳等于没有）。
3. 把 2 的时间戳套进 1 的区间。同秒成对 = 一个 turn 并发多次查询，正常。

实例 14 09-23 的闭环样本见记忆
`project_her14_perplexity_via_198_litellm_2026_09_23`。

## 6. DeepSeek 搜索（官方插件，截至 10-20 未发版）

OpenClaw 官方文档已写 DeepSeek web_search（docs.openclaw.ai/providers/deepseek#web-search），
实现在 GitHub `extensions/deepseek/web-search-provider.runtime.ts`（10-17 合入 main，#175729）：
直接调 `https://api.deepseek.com/v1/tools/search`，返回标题/链接/摘要/日期给主模型读，**不额外调大模型**。

```json5
tools: { web: { search: { provider: "deepseek" } } },
plugins: { entries: { deepseek: { config: { webSearch: { apiKey: "<DeepSeek key>" } } } } },
```

- 🔴 地址写死 api.deepseek.com，**不读 baseUrl ⇒ 不能经 198**，实例里得放真 DeepSeek key。
- 🔴 npm `@openclaw/deepseek-provider` latest `2026.10.5`、beta `2026.10.10-beta.2` 的 manifest **都还没有** `webSearchProviders`
  （判据：`npm pack` 后看 `openclaw.plugin.json#contracts`，别信文档）。插件 `pluginApi>=2026.10.x`，14 是 2026.8.1 ⇒ 要等发版 + 升实例。
- 那之前别自己在 198 造「搜索+flash 总结」转接——就是在重写这个插件（10-20 被用户批「闭门造车」）。
- DeepSeek 模型本身能不能搜见 [[litellm-198-web-search]] §3：flash 不能，只有 v4-pro。

## 7. 杭州 bot 也用同一套映射：比 14 多一跳，问题全在那一跳（10-21）

杭州 bot 的 websearch 链路是：bot → **杭州 gw**（`vllm` 47.96.23.21，litellm **1.101.0**，compose 非 K8s）
→ 198（key `carher-hangzhou`）→ per-key alias → `sa-grok-4.20-multi-agent`。
14 是 bot 直连 198，所以 **14 通了，杭州不一定通**。🔴 不要推翻映射方案，对着 14 逐跳比，只查多出来的那一跳。

| 层 | 症状 | 真因 / 修法 |
|---|---|---|
| 198 key | 401 `insufficient_quota` → 进冷却后 429 | 10-14 的 grok alias 只加在 13/14/75，`carher-hangzhou` 没有，请求直打 Perplexity。补 alias：`litellm-198-key-allowlist.py --prefix carher-hangzhou --only carher-hangzhou --alias perplexity-sonar=… --alias perplexity-sonar-search=…`（🔴 `--prefix` 必须给 `carher-hangzhou`，`carher-` 也行但别漏） |
| 杭州 gw 超时 | 408，`timeout value=10.0` | 杭州 `config.yaml` `request_timeout: 10`（10-15 router-tune 调的，全局）。只改两行 perplexity 模型：杭州 DB `litellm_params ||= {"timeout":60}`，不动全局 |
| 杭州 gw 解析 | 500 `Invalid response object` / `annotations.N.url_citation: Input should be a valid dictionary` | 198 chat→Responses 桥把 annotation **平铺**（`{type,url,title,…}`）；杭州 openai SDK 解出 `url_citation=None`，1.101.0 `Message` 校验失败。198 callback `chat_annotation_nest` 补嵌套 `url_citation:{…}`（平铺字段保留，14 插件两种都认）。10-21 三车道之 gray/prod 已上 |
| 杭州 gw 缓存 | 4ms 回 200、答「尚未公布」 | 杭州 `cache: true`（redis）吃到修好前的旧答案。测试题必须带 nonce；真实用户换个问法就不命中 |
| 198 兜底 | 200 但 ann=0、答「尚未公布」 | multi-agent 503 后走全局兜底 `sa-grok-4.20-multi-agent → deepseek-v4.1-flash`，flash 不搜。看 SpendLogs `model_group` 是不是 flash |
| grok 池 | 503 `Service temporarily unavailable`，~30s | sub2api 池只剩 1 条腿在服务（`sub2api-grok-onboard.py health`：`phase=routing account_id=NULL` 成千上万）⇒ 加号。**这条 14 和杭州同时挂** |

### 杭州侧怎么测才算数

- 🔴 **验解析修复别用 `Message(...)` 直接构造**：平铺形能过（假绿）。要走杭州真路径：
  openai SDK `construct_type(type_=ChatCompletion, value=raw)` → litellm `convert_to_model_response_object`，
  在 `llm-gateway-litellm-1` 容器里用 `/app/.venv/bin/python` 跑。
- 杭州机够不到 198 内网 NodePort（30402/30405 都 000），走公网 `https://cc.auto-link.com.cn/pro/v1`。
  对比 gray/prod 只能在 198 上用 `carher-hangzhou` 明文打 127.0.0.1:30405 / 30402 抓原始回包，再把回包 base64 走 `jms ssh vllm "bash -s"` 的 stdin 送进杭州容器解析
  （🔴 `jms scp` 会 `Permission denied`）。
- 明文 key 只在杭州 `/opt/llm-gateway/.env` 的 `REMOTE_LITELLM_API_KEY`，取用后 sha256 前 8 位对 `aa820a93`，用完删。
- 端到端：杭州机 `curl 127.0.0.1:4000/v1/chat/completions`（master key），两个名字 × 3~4 道**训练截止后**的新题，每题带 nonce；
  判据 = 200 + `annotations` 非空 + 答对。ann=0 的那发去 198 SpendLogs 看是不是落了 flash。
- 杭州容器日志判解析回归：`nerdctl logs -t --since 30m llm-gateway-litellm-1 | grep _handle_llm_api_exception | grep -c 'Invalid response object'`。
- 杭州 SpendLogs **只记成功、`proxy_server_request` 是空的**，看不出请求形状 ⇒ 请求形状只能去 198 SpendLogs 按 `api_key` 看。
- 198 SpendLogs 里 `carher-hangzhou` 的 perplexity 名流量 ~80% 是杭州 gw 健康检查（`Hey how's it going?` / `What's 1 + 1?`，`max_tokens:16`），
  算真实搜索量和成本前先按最后一条 message 排除这两句。

### 量具 L2 红了先看哪里（14 侧）

`hermestest-web-search-verify.py` 10-21 起 L2 会把插件报错原文打出来：
- `req: xxxxxxxx` ⇒ 网关报错，`cli-anything-litellm db req <id>` 读 198 原文，多半是 grok 池 503。
- `fetch-timeout … 30000ms` ⇒ 插件 30s 硬超时，198 那条可能已经 success（multi-agent 重查询 30s+ 常见），换短题再判。
