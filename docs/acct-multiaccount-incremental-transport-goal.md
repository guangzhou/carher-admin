# acct 多账户链路：增量传输目标书

> 文档定位：这是**目标与范围**文档，不是实施记录。实施进展见记忆
> `project_198_acct_encrypted_incremental_survey_2026_08_22` 与 skill
> `codex-multiturn-transport-mechanism`。
>
> 术语约定：本文档中的 **acct 多账户链路** = 198 生产上由多个 ChatGPT
> 账户组成的上游池链路（客户端 → 外层 litellm-proxy → acct-N pod → 上游）。
> 全文统一用「多账户」，不用「账号池」，以免与模型侧概念混淆。

## 主目标

**让 acct 多账户链路用上 codex 官方那套多轮机制——最终要的是增量传输（省流量 / 降延迟）。**

加密（encrypted_content 放行）是增量传输的**前置地基，不是目的本身**。

> 用户原话："加密不加密最终目标是增量传输。如果没有增量传输，我不知道它加密的价值对我们来说的价值在哪儿呢。"

即：加密先打通，是为了让"同一多轮会话跨请求复用上下文"成立；在此之上做增量传输，才是真正省流量降延迟的那一步。

## 硬约束

1. **换号 / 账户异常这层异常处理必须做扎实。**
   一个账户桶满时系统必须重试另一个账户（是系统换号，不是用户操作）。这一层没做好，会引发反复投诉——历史上正是因为这层没处理好，才把加密整个删掉过。任何放行加密 / 做增量的改动，都要保证"桶满切别的账户"这种日常场景不炸。

2. **改线上代码遵循可回滚、可验证、可灰度三原则。**

3. **验证要看实际发送内容，不能只看响应码。**
   200 ≠ 密文真到了上游。验证放行 / 增量是否生效，必须查实际发送内容（SpendLogs `proxy_server_request` 看值形态），不能只看 HTTP 状态码。

## 范围

- **在范围内**：加密放行的灰度与观察；增量传输（WS 四道闸门 / previous_response_id / 426 熔断降级）的可行性、落点、实现与灰度上线；换号异常处理。
- **不在范围内**：主账户续订 / 接码等账户运维；计价体系本身的改造（仅需在放行加密后评估账单影响并请示是否豁免）。

## 阶段拆解（概要）

- **阶段 0**：加密放行补丁收尾（清死代码、canary 挂真实实例）。
- **阶段 1**：真实流量下验证加密放行的收益与代价（缓存命中、是否偷懒、账单影响）——决策门：收益 > 代价才继续。
- **阶段 2**：增量传输——定落点 → 抓真实请求体分布量化收益 → 隔离环境实现 WS 四闸门 → 灰度上线。

（每步的输入 / 动作 / 预期输出 / 验收见记忆文件与本轮对话拆解。）

## 阶段进展（实测坐实，2026-08-22）

### 阶段 2 可行性已坐实：上游支持 WS 增量，端到端跑通

从 acct pod（chatgpt-acct-103）内以真实账户身份直连上游做的 live 实测：

- **上游支持 responses-over-WebSocket**：`wss://chatgpt.com/backend-api/codex/responses`
  握手拿到 **101 升级成功**（带头 `OpenAI-Beta: responses_websockets=2026-02-06`
  + `ChatGPT-Account-ID` + OAuth Bearer）。
- **两轮增量端到端通过**：T1 全量问「17×3+4」→ 答 55、拿 `response_id`；
  T2 **只发追问 +`previous_response_id`（不重发历史/密文）**→ 答 110（55×2），
  `enc_blocks=1`。**服务端从连接上下文拼回了历史**——这就是增量传输的核心机制在本环境真实可用的证据。
- **WS 帧信封形状实测确定**：`{"type":"response.create", <HTTP 14 字段平铺>,
  "previous_response_id":…, "generate":…}`（不是嵌在 `response` 里，也不是纯扁平无 type）。
- **账户接受的 slug = web slug**：`gpt-5.6-sol` / `gpt-5.6-terra` / `gpt-5.5` 均 OK；
  `gpt-5` / `gpt-5-codex` / `codex-mini-latest` 被拒（`model not supported when using
  Codex with a ChatGPT account`）。

### 阶段 1 收益已量化（修正原估）

SpendLogs 30 分钟窗（acct aresponses，`proxy_server_request` 逻辑体大小）：

| 指标 | 值 |
|---|---|
| 请求数 | 867 / 30min（≈4.18 万/天） |
| 请求体均值 | 328 KB（p50 327 / p90 580 / max 732） |
| 多轮回放密文占比 | **95%** |
| 逻辑出网 | 278 MB / 30min → **≈13.4 GB/天** |

原估 18GB/天偏高，实测 **≈13.4 GB/天**；其中 **95% 是回放历史的多轮请求，正是增量可消除的部分**——增量把 R2/R3 轮的重复历史砍掉，理论可省该量级的大头。收益方向坐实。

> 方法论边界：13.4GB/天是 SpendLogs 记录的**入站请求体**逻辑大小外推（非抓包实测出网字节）；acct pod 是 LiteLLM，向上游发的是解包后 HTTP 明文体（无 zstd），量级同阶。作为可行性估算够用，精确出网需抓包。

### 阶段 0 待办状态

- normalize v2 补丁：config 与 litellm-callbacks CM 均确认仍接线（canary 名单 +
  warning 计数代码在）。但 proxy pod stdout **零日志输出**（logging 被关/重定向），
  无法从日志证明钩子正在 fire；决定性验证需重开日志或做 in-band 探针。**列为后续，非主目标阻塞项。**
- 观测到 litellm-proxy 正在频繁滚动（本轮内 55m→11m 两次新 pod），需留意是否有外部 churn。

## 收官报告（2026-08-24 12:30，全池实测口径）

- **出网削减（实测非外推）**：全池 6h 窗 11,763 个增量轮，实发 298MB；HTTP 等价
  ≈11,763×159KB≈1,870MB → **省 1.57GB/6h ≈ 6.3GB/天**（周末口径；工作日流量更大则更高）。
  命中率 79.2%（11,763/14,851）。
- **降延迟（缓存实证）**：同时段昨今对比（分段控制大小），上游缓存命中
  大上下文 58.5%→74.3%、中型 30.1%→65.7%、**加权总体 ≈55%→74%（+18pp）**。
- 三硬约束全程有效：真桶满换号/12+15 演练/5 次实战秒级回滚/帧级日志归因。
- **本目标书宣布关闭**。后续接力：压缩已默认全量开（docs/gateway-compaction-*）、
  WS ingress 待 S4（docs/ws-ingress-*）。
