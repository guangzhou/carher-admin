## 两个承重发现

### ① "envelope miss" 日志 = prose 答案的**默认出口**,不是失败信号
pod 日志窗口内 `[stall] envelope miss -> retry disabled, returning first pass (N chars)` 共 **11 条,
恰好 = 11 个聊天型请求**(1 探测 + 10 聊天)。即:这条线上**每一个合法纯聊天回答都从"打捞"分支出门**。
- 含义 A:此前把 "returning first pass" 当"垃圾交付点"的判断要修正——它**既是**垃圾出口(当 first pass
  真是垃圾时)**也是**唯一的 prose 正常出口(当答案就是 prose 时),两者在代码上不可区分——
  **这正是"结局无三分法"的病理标本**:合法终态和失败终态共享同一条代码路径同一行日志。
- 含义 B:新协议把 "prose 答案" 设为合法终态后,这层日志噪声消失,监控才有信号可言。

### ② 真病灶:超短指令答非所问(ll 3/3,系统性)
`ll`(2 字符指令,期望列目录)三轮全部回了问候语("你好,我在。想做什么?")。对照:`ls` 4/4 调工具,
`task`(中文明确指令)3/3 调工具。**失败形态不是"半截/近空",是"把指令当寒暄"**——r16 修掉的是
误杀合法短答,这个是模型侧把短输入误读,属"该动手没动手"家族。占比:3/30 用户轮 = 10%
(集中于超短指令场景)。

## 分叉门判定(交用户)

**r16 前的立项病(8/16 近空)已经不存在了:近空/半截 = 0/27。** 剩余的病:
1. `ll` 型短指令误读(模型侧,10%,协议重写**不直接治**——这是理解问题不是协议问题;
   可用 prompt 契约缓解,S3 P-a 数据会说话);
2. 架构债(五条级联重试路+合法/失败共用出口,①的病理标本)——**重写治的是这个**,
   收益是可维护性/可观测性/垃圾出口封死,不是失败率大降。
