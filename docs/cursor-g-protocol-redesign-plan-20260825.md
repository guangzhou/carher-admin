## 0. 真实目标(复述)

把 cursor-g **网页线**「近空 / 哑火 / 1 字符 / 半信封」这一类不稳,**从协议层根治**:
用一条确定性的**轮次契约**(单终止符 + call_id 配对 + 只收闭合信封 + 失败整轮从历史重建重发)
**替掉**现在那堆症状补丁(r14 三通道收割、r16 near-empty 救 + stall 门)。灵感照搬 Codex harness
的「协议与内容结构分离 + 发送前硬校验配对」纪律。

**心智模型(用户要求铭记):** 大模型是脑,agent 是手脚,脑指挥手脚**靠协议**。不稳先修协议,不堆补丁。

**成功定义:** 这类失败率结构性下降,且**不引入重复吐字 / 回退黑洞 / 延迟回退**。
**诚实天花板:** Codex 的终止符是服务端结构性事件,不可能"忘发";我们的终止符终究是模型吐的文本,这个差距网页面抹不掉。**新协议承诺的不是消灭失败,而是把失败从"吐 1 字符垃圾"变成"一次干净重试或一个诚实报错"——确定性处理,非玄学兜底。**

### 0.1 设计五原则(2026-08-25 二刷 + 08-26 五趟精读后定稿,S4 设计稿必须遵守;原文锚点见精读笔记)

1. **控制流在网关,模型只填格子(不让模型"选",网关来"分配")**:不依赖模型在流里吐判别符表态;利用现有两趟结构把模式钉死在轮次里——**第一趟合法产物只有 {信封 | DONE},第二趟合法产物只有 {人话答案+终止记号}**,每趟一种合法输出类型,歧义无从产生。(Codex:收工判据=工具item/end_turn位/队列三个结构信号取OR,零长度启发式,turn.rs:2397/2577;stream_events_utils.rs:326。)
2. **重试三层 + 错误分类,重试是特权不是默认**:①网络/CF 抖动走专列宽松等(5s→60s 封顶);②常规瞬态错(流断/5xx/**烂JSON信封**)预算内重建,**服务端建议延迟优先于本地 backoff**;③**确定性失败零重试**(空 completion 恒定复现、额度尽、登录态死——前科:xhigh 连续 4 次一致空)。预算耗尽或换路径兜底时**预算重置**给兜底一次公平机会;终局=给 Cursor **诚实报错**,绝不无声空转。(Codex:responses_retry.rs:58-83/102-126/85-100;error.rs:364 不可重试23类 vs 可重试11类。)
3. **协议趟零字节外流**:第一趟信封网关内部消化、不给客户端流任何字节 → 第一趟可自由重试、零重复风险;"首字节前才能重试"约束只剩第二趟要守。(Codex:delta 只给 UI、不落史,只闭合 item 落史,turn.rs:2114。)
4. **出口边界幂等校验,历史允许脏**:call/output 配对、孤儿处理不在写入点维护,而在**每次向上游构建请求时全量幂等重跑**——缺结果=原位合成 `"aborted"`(**id 确定性**,同一孤儿重建N次同一id,保 conv 前缀稳定);缺调用=删。(Codex:normalize 唯一调用链=for_prompt 出口,history.rs:206/218/450;normalize.rs:19-127。)
5. **结局三分法,噪声宽容、结局严格**:每轮结局必须落进 {完整终止 | 显式失败 | 无终止半截(incomplete)} 三类之一,"没说完"是协议一等公民而非异常;中途文本噪声可容忍,**"怎么结束的"零含糊**——半截=incomplete=废轮重建,永不打捞。(Codex:completed/failed/incomplete 三事件,responses.rs:408/453/464;EOF无completed=硬错:565。)

## 1. 底线与原则(验收一票否决)

1. **不影响现有成果**:cursor-g 网页线现在能用的能力(工具执行、组池、延迟)不许退化。
2. **不影响其他通道(codex 首当其冲)**:codex 原生 FC 线(`cursor-fc-*`,CM `zk-cursor-protocol-patch`)、
   codex CLI 线(`zk-image-patch`/bpi-codex.js)行为必须**逐轮不变**。**改我这条线却让 codex 出问题 = 直接判死、回滚。**
3. **只碰代码,不碰账号面**:acct82 账号被网页线与 codex CLI 线共用,但共用的是账号/token/会话记忆**不是代码**;
   重写只改 `responses.js` 逻辑,**绝不动账号记忆 / 自定义指令 / token**。
4. **改动面收敛到独占文件**:落地只在 `responses.js`(CM `zk-cursor-bpi-patch`,只挂 `zero-cursor-bpi` +
   `zero-cursor-bpi-82` 两 pod)。**唯一共享面 hook `cursor_web_fc_sys_rewrite.py` 能不动就不动**;非动不可守住
   prefix gate + fail-open,并把 codex/其他 web 线纳入回归。**WA 代码一行不动**。
5. **零中断 + env-gate 默认关 + 字节级可回滚**:新契约默认关,只在金丝雀 lane 开;不达标一键回滚到 CM 备份。
6. **不在生产 her 实例做实验**:实验只在 carher-1000 / 临时 scoped key。
7. **无证据不下结论**:任何「X 导致 Y」先给证伪条件与数据;代码存在 ≠ 该路径被执行。

## 3. 最小可执行步骤(不跳步)

### S0 建 codex 线回归脚本(底线可验证的前置)
- **输入**:临时 scoped key(授 codex 线一个 `cursor-fc-*` 模型;用完即删)
- **动作**:写一个固定问答脚本(一问一答 + 一个单工具轮),对 codex 线跑,记录基线行为。**轮数压最小(烧 codex 额度)**
- **预期输出**:`codex_regress.py` + 一份 codex 线基线结果(可复现)
- **验收**:脚本可重复跑、结果稳定;这是后续每次 patch 的对照基准

### S1 立网页线基线(⚠️ 当前真实失败率未知,本步同时是必要性复核)
- **输入**:**真 Cursor 客户端 + liuguoxian04 账户(key04)**——这是全程的验证身份;101/key03 是生产,不做实验。发真实三类轮次(纯聊天/单工具/多工具,合计 ≥30 轮,可分散在正常使用里攒)
- **动作**:逐轮记结果形态,**按三分法归类:{完整终止 | 显式失败 | 无终止半截},形态学(近空/半信封/哑火)作为半截类的子标签**——基线与 S6 金丝雀用同一套结局分类学,否则前后不可比;口径三对齐:Cursor Structured Logs × bpi pod 日志 × SpendLogs(仅时间戳,token 是合成的不可用)
- **⚠️ 流量钉死前提(防假数据)**:必须先确认 key04 的请求确实落在预期 lane——用冻结的 82 直连调试名(`cursor-web-fc-82-*`)或验证 WA key 亲和钉死,**在 pod 日志里 grep 到自己的暗号才算数**。测的流量打错 lane,整张基线作废
- **预期输出**:一张 **r16 修复后**的「失败率 + 形态分布」基线表
- **验收**:样本 ≥30 轮、三类全覆盖、每轮在 pod 日志有对应记录
- **⚠️ 分叉门**:立项依据「8/16 近空」采样于 **r16 之前**;r16 上线后已观测到 stall near-empty 归零。**若 S1 显示失败率已经很低,重写的必要性回到用户重新拍板**(可能降级为只做 call_id 配对等低风险子项,或搁置)

### S2 实读代码 + 坐实隔离 + 定金丝雀钉死方式
- **输入**:198 CM `zk-cursor-bpi-patch` 的 `responses.js`;各 lane 的 model_info / 账号映射;key04 的模型授权表
- **动作**:①标出收割、stall、near-empty 救、fresh-conv 重建、call_id 五处的 file:line;②核对哪些 pod 挂本 CM(证 I4/I5);③查每条 lane 绑的账号是否与 codex 共用;④**确定 key04→金丝雀 lane 的流量钉死方式**(82 直连调试名 vs WA 亲和,并实测验证);⑤**定位"已收割信封/工具结果"的落账时点与 conv 树持久锚点**——证"断点续跑"可行性(重建时已收割的信封是否已在 conv 历史里,重发能否只补断点之后,对应原则 4 的账本前提)
- **预期输出**:「现状五处 → 拟被哪条契约替换」映射表 + 「金丝雀 lane 选谁 + 怎么钉死」结论(附账号映射与路由证据)
- **验收**:每处有 file:line 不靠记忆;隔离与钉死结论有实测证据(非推断)

### S3 探「模型服从率」双记号探针(按原则 1/5 重定义;探的是协议的两个模型侧承重点)
- **输入**:临时 key(用完即删)
- **动作**:两个探针分开测,各 ≥20 轮:
  - **P-a 趟内单一产物**(原则 1 的承重点):第一趟加「本轮只允许输出一个信封或字面 DONE」约束,统计服从率与失误形态(混出人话/半信封/空);
  - **P-b 终止记号**(原则 5 的承重点):第二趟加「答案末尾必须以 ⟨END⟩ 结尾」约束,统计漏吐率与错位形态;
  - **P-c(可选加严臂)**:终止记号带 item 计数(如 `⟨END:2⟩`)——**这是超出 Codex 的自选动作**(Codex 的 completed 不带清单校验,是因为它传输层可信、我们传输层是模型嘴),只有 P-b 服从率高且 P-c 不显著拉低服从率才考虑;
  - 对照组:现行 prompt 不变跑同样轮次
- **预期输出**:两(或三)个探针各自的服从率 + 失误形态分布(**本步只产数据,不做取舍**)
- **验收**:每探针 ≥20 轮、可复现;**取舍在 S4 拿数据定,阈值不许拍脑袋**(阈值必须能被 S3 数据证伪)。任一记号服从率不济,该子项砍掉——**废轮重建+预算+诚实报错链路才是承重墙,记号只是第一道闸**

### S4 出设计稿(过目,不动生产代码)
- **输入**:S1–S3 结果 + 第 6 项(灰度范围/阈值)你的拍板
- **动作**:写设计稿,**必须遵守 §0.1 设计五原则**,且至少包含五个交付件:
  ①**轮次状态机**(每轮结局落进三分法 {完整|失败|半截},半截=废轮重建,无打捞分支);
  ②**错误分类表**(照精读笔记第 3 趟的初稿细化:哪类零重试、哪类预算内、哪类专列宽松等,延迟取值顺序=服务端建议→本地 backoff);
  ③**出口 normalize 规格**(每次向上游发请求前幂等跑:缺 output 原位合成 aborted+确定性 id,缺 call 删);
  ④**代码替换映射**(S2 的五处现状各自被哪条契约替换/删除);
  ⑤**灰度与回滚**(env-gate 开关、gate-off 等价性、CM 字节级备份、codex 回归挂钩点)
- **预期输出**:可评审设计文档
- **验收**:**用户点头**才进 S5

### S5 金丝雀实现(单 lane,env-gate 默认关)
- **输入**:S4 设计 + S2 选定的金丝雀 lane
- **动作**:新契约写进 `responses.js`,env 变量控制、默认关;`node --check` + 回归台架过再 `kubectl patch --type merge` CM;先备份 CM 到 `/home/cltx/backups-bpi/`;只重启金丝雀 deployment 并对它 `kubectl set env` 打开
- **⚠️ 隔离真相**:CM 被 101/82 **两条 lane 共挂**——patch 后新代码两边都落盘,金丝雀隔离靠「只重启一条 + 只在它开 env」。若非金丝雀 lane 意外重启(OOM/漂移),它会带新代码起来(gate 关)。**因此 gate-off 路径必须与旧行为等价,且这条要单独验**
- **预期输出**:金丝雀 lane 跑新契约;另一条 lane + codex 线保持原样
- **验收**:node 检查过、回归台架过、金丝雀能出字、CM 有字节级备份、**gate-off 等价性已验**(env 关着跑 S1 脚本抽样,行为与旧版一致)

### S6 验收对照(网页线 + codex 线双闸)
- **输入**:S1 同一套 Cursor 真实轮次(**liuguoxian04 账户打金丝雀 lane**)+ S0 codex 脚本
- **动作**:①04 在 Cursor 上对金丝雀 lane 重跑 S1 三类轮次;对照 = 未改 lane(101/key03 生产流量**只被动看日志,不做实验**);②codex 线跑 S0 脚本对照改前

- **验收(全部满足才算过)**:金丝雀失败率显著低于 S1 基线 **且** 零重复吐字 **且** 零新增黑洞(重试预算耗尽必须落诚实报错,pod 日志可查) **且** **延迟不劣于 S1 基线**(r16 已砍到 ~9s,不许拆东墙) **且 codex 线行为逐轮不变** **且** 对照 lane 被动日志无异常升高 **且** **金丝雀期每轮结局都被三分法计数器记录**(pod 日志一轮一行 `[turn-verdict] completed|failed|incomplete`,这同时是上线后的长期监控口径——用结构化结局计数替掉旧启发式散点日志);任一不满足 → 回滚

### S7 推广或回滚

## 5. 现行 vs 新方案对比 + 用户体验承诺(验收挂钩,2026-08-26 补)

> 本节每一行都不是宣传词,是**可证伪的验收项**:右列写明在哪一步、用什么证据判过/不过。
> S6 总验收时逐行打钩,任何一行验不上 = 该项承诺不成立,回滚或降级。

### 5.1 工程对比(现行 r8–r18 → 新协议)

| 维度 | 现行 | 新方案 | 验收方式(哪步/什么证据) |
|---|---|---|---|
| 判轮次好坏 | 长度门(<24)、hadToolResult、"只说不做"检测……一病一门,会误杀(r16 前科 12/12) | 每趟单一合法产物 + 结局三分法,零长度启发式 | S5:代码中不存在任何长度阈值判据(diff 审查);S6:合法短答("辰"类)0 误杀 |
| 失败处置 | 凑合交付 1 字符 或 fresh-conv 全量重问(17k 重发) | 断点重建(已收割信封不丢)+ 预算 1–2 次 + 诚实报错 | S6:pod 日志无 "returning first pass (N chars)" 类打捞行;重建轮日志可见断点续跑(不含已收割信封重发) |
| 错误分类 | 无,一锅烩 | 三层:网络宽松等 / 瞬态预算内 / 确定性零重试 | S5 单测:三类错各注入一次,走向正确;S6:确定性失败(如额度尽)日志显示 0 次无效重试 |
| 配对 | 邻接猜 | call_id + 出口幂等 normalize(缺果补 aborted / 缺因删) | S5 单测:构造孤儿场景,出站请求无孤儿;S6:上游请求抽查 0 孤儿 |
| 新失败态维护成本 | 加新补丁(无界) | 自动落"半截"桶走重建,不改代码(有界) | S6 期间出现的**未预见**失败形态,必须已被三分法接住(有 turn-verdict 记录、无未定义行为)——出现一例走不进三桶的 = 不过 |
| 可观测 | 散点启发式日志 | 一轮一行 `[turn-verdict] completed\|failed\|incomplete` | S6:金丝雀期每轮都有且仅有一行 verdict,计数与 Cursor 侧对得上 |

### 5.2 用户体验四承诺(以使用者视角验收)

| # | 承诺 | 验收方式 |
|---|---|---|
| U1 | **收不到废话轮**:要么正经答案,要么明确报错,没有第三种暧昧态(1 字符/半截 JSON/装聋) | S6:金丝雀 ≥30 轮,交付物 100% ∈ {完整答案, 明确错误};出现一次垃圾交付 = 不过 |
| U2 | **坏时死得明白**:确定性失败几秒内给人话报错,不吊着转圈 | S6:注入一次确定性失败(如临时收回模型授权),Cursor 侧 <10s 内收到可读错误 |
| U3 | **失败恢复无感/低感**:多数瞬态失败被断点重建吃掉,用户只觉得该轮稍慢 | S6:瞬态失败轮中,最终成功交付的占比 ≥(S4 定,基于 S3 数据);且重建轮延迟 < fresh-conv 全量重问的历史均值 |
| U4 | **好的时候没变化**:正常轮延迟与现行持平(~9s 基线) | S6:延迟闸——金丝雀正常轮延迟不劣于 S1 基线 |

### 5.3 诚实边界(不承诺项,写死防止验收时偷换目标)

- **不承诺**模型犯病次数变少(③ 未知,只有 S3/S6 数据能说话);
- **不承诺**失败轮比"直接吐垃圾"快——重试有时间成本,取舍是"慢几秒拿真答案 > 秒回垃圾",由 U3/U4 双闸兜住;
- **不碰**防 bot 四堵墙与网页线 best-effort 本质。
