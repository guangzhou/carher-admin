## 1. 轮次状态机(核心交付件①)

```
请求进入(带 tools 的 Cursor 轮)
  └─ 上游流结束,收口判定(finish 一次性,替代现行五条级联路):
       [1] 收割到 ≥1 个闭合信封/⟦cmd⟧/sandbox 代码 → verdict=COMPLETE(tool_call 交付)
       [2] 无收割,prose 非空                        → verdict=COMPLETE(答案交付)★合法终态,不再是"打捞"
       [3] response 层错误/HTTP 错误                → verdict=FAILED
       [4] 0 字符 / 流无终止 / 半截信封(``` 开了没闭)→ verdict=INCOMPLETE
  └─ INCOMPLETE/FAILED(可重试类)→ 重建重发(同 conv 断点,预算 1;首字节前窗口)
       → 再失败 → 诚实报错给 Cursor(SSE error event,人话)
  └─ 每轮末尾必打一行:[turn-verdict] complete|failed|incomplete cls=<chat|tool> retry=<n>
```

要点:
- **[2] 是本设计的灵魂**:S1 证明 11/11 合法 prose 都在走"miss 打捞"分支——合法终态与失败终态
  共用出口。三分法把它们劈开,监控才有信号。
- 现行 near-empty 救(len<24)、act-retry(_REFUSE_RE/_PLAN_RE)、escalate、⟦重问、envelope-retry
  五条路 → 塌缩为一个收口判定 + 一个统一重试预算。正则拒答检测降级为 INCOMPLETE 的子分类器
  (可保留一次 kick,计入同一预算,不再独立计数)。

## 2. 错误分类表(交付件②,照精读第3趟)

| 网页线现象 | 分类 | 处置 |
|---|---|---|
| 流断/超时/5xx/上游 gap 不恢复 | 瞬态 | 预算内(1 次)同 conv 重建 |
| 半截信封/烂 JSON | 瞬态(codex: Json=可重试) | 同上,**永不打捞半截** |
| CF 403/网络抖 | 瞬态-网络 | 同上(该线由底层 curl 栈处理,不额外加层) |
| 0 字符 + 同输入重试仍 0 | **确定性** | 零二次重试,诚实报错(xhigh 前科) |
| 额度尽/登录态死(401/429 带明示) | 确定性 | 诚实报错 + 日志标注 lane 换线建议 |
| 服务端明示 retry-after | 瞬态 | 认服务端延迟 |

## 3. 出口 normalize(交付件③,新增,codex history.rs:206 同型)

每次向上游发续轮 prompt 前幂等跑:
- 输入里有 function_call 无对应 output → 原位合成 `[TOOL RESULT <call_id>]\naborted`(**确定性 id**:
  用 call 内容哈希,不再 randomBytes——同一孤儿重建 N 次同一文本,保 conv 前缀稳定);
- 有 output 无 call → 剥除;
- 现行 `[TOOL RESULT ${call_id}]` 文本回灌格式保留(它就是我们的"配对槽")。

### 取舍落定

- 全量版第一趟契约(§7)模型侧可行(P-a 满分),但 **S1 显示无必要性支撑**(近空=0)——维持降级版推荐;
- ll 病灶移出本项目范围,标记"已知局限+conv 语境依赖",不做投机性 prompt 修补。
